## Diagnosis and minimal change

The old revision explicitly supplied the public `wss://transcendence.koreacentral.cloudapp.azure.com/ws`. The task baseline omitted `client.webSocketURL` when `VUE_APP_DEV_WEBSOCKET_URL` was absent or empty. Installed Vue CLI 5.0.8 then constructs its development client URL from the inferred LAN address unless its container heuristic succeeds (`frontend/node_modules/@vue/cli-service/lib/commands/serve.js:139`). Its existing container branch already uses `auto://0.0.0.0:0/ws`. Container detection is a heuristic, not proof of the operational process state.

Root independently observed the operating public `/login` document and scripts returning HTTPS 200 from public address `20.194.105.25`, followed by an actual HMR WebSocket attempt to `ws://172.18.0.3:3000/ws`, initiated by the webpack client resource query. No guest click or `/auth/guest` request occurred. The public bundles include the same private HMR query. This confirms a public page producing a private HMR request. The precise permission popup, blocked reason and WebSocket remote address were not directly verified. The public probe's final process exited 1 after stdin EOF; the collected JSON is evidence, not an overall successful probe. Operational env/cgroup/proxy selection remains unavailable. See root's public network and bundle-fingerprint records.

The fix at `frontend/vue.config.js:13` uses the explicit override when set and otherwise uses `auto://0.0.0.0:0/ws`. Installed webpack-dev-server 4.9.3 parses this config string; its client replaces wildcard hostname with the browser hostname, auto protocol with the browser protocol, and zero port with the browser port (`client/utils/createSocketURL.js:75–115`). `auto://` is configuration syntax; no browser request should target that string or literal `0.0.0.0`.

Existing allowed hosts are unchanged. Public/local explicit overrides remain authoritative. An explicitly configured private address remains a configuration risk: the negative test documents that boundary; it does not claim to block every private address or private DNS result. A fixed public WSS default would restore the old public host but would also send direct local development traffic there. The browser-derived default supports both while retaining explicit deployment overrides. No API/game/chat URL refactor or socket disabling was needed.

## Independent URL evidence

`evidence/public-bundle-endpoint-expressions.json` parses only relevant expressions from the observed public `app.js` and records its SHA256. The inspected embedded object has no `VUE_APP_BACKEND_URL` key for main Axios, Login or FriendsSlider; those expressions fall back to `window.location.origin`. It has no `VUE_APP_WS_URL` key for the route game socket or router chat socket; those expressions fall back to `window.location.origin.replace(/^http/, 'ws')`. This is compiled-expression evidence from this asset, not authenticated `/user/me`, image, game or chat traffic, and not a claim about unread lazy chunks or the full operating process env.

Repository code uses Axios/API and image base `VUE_APP_BACKEND_URL || origin`; `/game` and `/chat` are Socket.IO namespaces using `VUE_APP_WS_URL || origin` with the usual `/socket.io/` transport path. They are distinct from webpack HMR `/ws`. Backend `FRONT_URL` controls authentication redirects. Frontend Dockerfile still uses `yarn serve --host 0.0.0.0`, as it did in the old revision. Compose supplies frontend/backend env files. No repository proxy or selected operational override was available to verify.

No actual local `.env*` URL configuration was found in the inspected root/frontend/backend locations and relevant inherited URL keys were absent at preflight. This says nothing about operational files. Installed Vue CLI loads mode local, mode, local, base env in that priority; inherited process values win. `VUE_APP_*` is embedded during build/serve, so changing env requires creating and serving the resulting new bundle. Compose env_file feeds process env and may be overridden by higher-priority explicit settings. Avoid printing whole env files or embedding credentials in endpoint evidence.

## Official version context

- [Chrome 147 release notes](https://developer.chrome.com/release-notes/147): local-address WebSockets fall under LNA; main-frame navigation is exempt. The earlier Chrome 138 statement excluding WebSockets is not the current rule. Observed public probe/browser fixture version is Chrome 152.
- [Webpack dev-server configuration](https://webpack.js.org/configuration/dev-server/#websocketurl): current docs explain the auto URL format, but currently describe v5. The installed v4.9.3 source and executed test are the compatibility evidence for this repository.
- [Vue CLI modes and environment](https://cli.vuejs.org/guide/mode-and-env.html): env priority and compile-time embedding.
- [Compose environment precedence](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/): process/container configuration priority; a host env file alone does not prove a browser runtime value.
